# Batch subscriptions

A consumer can submit several API/plan selections together. Daikoku stores one
`SubscriptionBatchDemand` parent and one ordinary `SubscriptionDemand` child per
selected plan. The parent groups producer approvals and tracks independent
outcomes; it does not replace the existing subscription workflow.

## Consumer selection

The multi-API flow preserves selected APIs across catalog pages. The consumer
first chooses a team using the existing team selector, then chooses plans and
keyrings. In environment mode, compatible plans with the same environment name
can share one new or existing keyring across APIs. Different Otoroshi bindings
or read-only settings form separate groups; plans that forbid aggregation keep
individual keyrings.

Already subscribed plans without multiple-key support, pending unit requests,
open batch items, unauthorized plans and unsupported processes are excluded.

The submission contains the consumer team, API/plan pairs, keyring choices, an
idempotency key and optional motivation answers. For example:

```json
{
  "team": "consumer-team",
  "idempotencyKey": "selection-2026-10-15",
  "items": [
    {
      "api": "catalog",
      "plan": "dev",
      "keyringChoice": { "type": "new", "creation": "dev-keyring" }
    },
    {
      "api": "billing",
      "plan": "dev",
      "keyringChoice": { "type": "new", "creation": "dev-keyring" }
    }
  ],
  "newKeyrings": [
    { "id": "dev-keyring", "customName": "Development APIs" }
  ]
}
```

The tenant and requester come from the authenticated context. The server
validates the whole selection before saving the parent. An invalid selection
rejects the submission, rather than silently creating a partial selection.
Repeating the same submission key reuses the existing batch.

## Direct progression, without a scheduled job

Submission prepares the selected keyrings, creates all eligible children and
advances their workflows in the same action. There is no periodic batch job,
global scan, slice size or delayed creation of the next group of children.

```text
Submission
   |
   +-- validate and persist the parent
   +-- prepare each shared keyring once
   +-- create all eligible child demands
   +-- advance executable children
           |
           +-- automatic HTTP step: one call per child, sequentially
           +-- producer approval: one notification per API and phase
           +-- human input or callback: persist and wait
           +-- completion: save the independent outcome
```

Producer decisions and form/email validation continue the affected batch
directly. If advancing one child opens a phase barrier for an earlier sibling,
that sibling continues within the same action. Waiting for input does not
schedule background work.

Cancellation, explicit failure reconciliation and the `_resume` action also
operate directly on the requested batch. After a server interruption, use
`POST /api/subscription/team/:teamId/batches/:batchId/_resume` to continue
persisted work. There is no automatic restart scan.

Deleting an API, plan, consumer team or requester blocks the affected items and
directly reconciles their batches, including unused keyring cleanup.

## Grouped approvals and partial results

Children of the same API advance by phase: the next phase waits until all
participating children have resolved the preceding phase. Finished children
do not block the remaining ones; other APIs progress independently.

A `TeamAdmin` phase creates one `ApiSubscriptionBatch` notification containing
the exact child demands and steps to decide. Accepting or rejecting it updates
the children and parent transactionally, then immediately continues the batch.
HTTP validation remains individual: one plan can be refused without canceling
the other plans.

Item states are `pending`, `waiting`, `inProgress`, `retryableError`, `accepted`,
`refused`, `blocked`, `failed` or `canceled`. The parent's state is derived from
its items and can finish as `partiallyAccepted`.

## Shared keyring lifecycle

Before creating children, Daikoku persists stable keyring identifiers and
credentials. Internal keyrings are ready immediately. For Otoroshi, Daikoku
creates or verifies its managed empty group, then creates a disabled API key
authorized only on that group. The keyring becomes ready only after successful
preparation.

When the first child is accepted, Daikoku activates the keyring and replaces
the empty-group authorization with the accepted plan's entities. Further
accepted children add their rights to the same keyring. Refused children do not
remove previously granted access. An unused shell is removed when all its
items finish without an accepted subscription, including after cancellation.

If preparation fails, the request reports the error. Retrying reuses the saved
identifiers and checks the Otoroshi key's ownership instead of generating new
credentials.

## Concurrent actions and uncertain external results

Before executing a child, Daikoku reserves its item and target keyring in
PostgreSQL. The keyring lock is shared across batches, preventing concurrent
operations on the same keyring. Revision guards and transactions protect
parent/child updates.

These protections remain necessary even without a scheduled job: a user can
repeat an action or two callbacks can arrive concurrently. Reservation expiry
does **not** authorize replaying an uncertain external operation.

The reservation duration defaults to 600,000 ms and is configured with
`daikoku.subscriptionBatch.reservationDuration` or
`DAIKOKU_SUBSCRIPTION_BATCH_RESERVATION_DURATION`.

A technical error is reported without preventing independent children from
being processed. An uncertain child result remains recorded until a producer
team administrator has verified the external outcome. Only after confirming
failure should they call:

```text
POST /api/subscription/team/:teamId/batches/:batchId/items/:itemId/_reconcile-failure
```

This releases the reservation, restores the executable child state and directly
continues the batch. Do not use it while the external outcome is still unknown.
