Remote catalogs

A remote catalog keeps tenant entities in sync with files kept outside Daikoku: a Git repository (GitHub, GitLab), an HTTP endpoint or a folder on the server. The files are the source of truth: what you add, change or remove there is created, updated or removed in Daikoku.

Managed kinds: team, usage-plan, api, keyring, api-subscription, cms-page, api-documentation-page. The reference shows a complete document of each.

Catalogs are managed by tenant admins, in the tenant settings, under Remote catalogs.

How a run works​

A run is all or nothing.

  1. Read. Daikoku fetches and parses every file. An unreadable file, an invalid YAML/JSON document, a document without _id, kind or _tenant, or a _tenant other than the catalog's fails the run. Nothing is applied.
  2. Validate. Every document is validated as the admin API would, against the database and the other documents of the run: an API may reference a plan declared in the same run. Any error fails the run. Nothing is applied.
  3. Apply. Writes go one by one in dependency order: team, cms-page, api-documentation-page, usage-plan, api, keyring, api-subscription. Removals go in reverse order. The first write error stops the run with the status partial. There is no rollback.

Every error is reported with its file, so one run lists all the problems at once.

Ownership​

Each entity written by a catalog carries the metadata created_by: remote_catalog=<catalog id>.

  • A catalog only updates and removes the entities carrying its tag.
  • An entity that already exists without a tag (created by hand) is refused, unless the catalog has Adopt existing entities on: it is then overwritten and tagged.
  • An entity tagged by another catalog is always refused.
  • On an update, some fields keep their value in Daikoku whatever the files say: the stars, issues, posts and issue tags of an API, and the test configuration (testing) of an API or a plan, set in the back office with its Otoroshi key.
note

A run writes the desired state directly. It does not trigger the side effects of the back office: changing the state of an API through a catalog does not notify its subscribers.

SettingEffect
SourceWhere the files are read, see below.
SchedulingOpts the catalog in the background job (see Operators).
Allowed kindsRestricts the kinds the catalog may declare. Empty: all.

Adopt existing entitiesTakes over the untagged entities the files describe. Meant for a one-off migration, see Move an existing tenant.

Sources​

KindConfiguration
github, gitlabrepo (owner/name, or an organization / group with repo_patterns), branch (default main), path (file, listing or folder), token, base_url for self-hosted instances, recursive to read subfolders.
httpurl (a document or a listing), headers, timeout in ms (default 30000).
filepath on the server (file, listing or folder), recursive, pre_command. Disabled unless the instance allows it: until then the back office does not offer it and a catalog using it cannot be saved.

Actions​

  • Deploy: runs now and applies. The report shows the changes of each updated entity, field by field: removed lines in red, added lines in green.
  • Test: the same run without writing anything, with the same report. Use it to preview a change.
  • Undeploy: removes every entity tagged by the catalog. The catalog is kept.
  • History: the last 20 runs with their created, updated, deleted and detached entities and their errors, without the changes. A run is completed, partial (stopped during the apply) or failed (nothing applied).
  • CI & webhook: the catalog token and the webhook URL, see CI and webhooks.
  • Delete: removes the catalog and detaches its entities, which stay in Daikoku. Run Undeploy first to delete them too.

One run at a time per tenant: a deploy started while another one runs is refused.

Operators​

KeyDefaultEffect
daikoku.remoteCatalogJob.enabledfalseStarts the background job.
daikoku.remoteCatalogJob.modeintervalinterval or cron.
daikoku.remoteCatalogJob.interval60000Period in ms, in interval mode.
daikoku.remoteCatalogJob.cronExpressionCron expression, in cron mode.
daikoku.remoteCatalogJob.keysecretKey of POST /api/jobs/remote-catalog/_sync?key=<key>, which runs the job now for the tenant of the request domain.
daikoku.remoteCatalogJob.allowFileSourcefalseAllows the file source (DAIKOKU_REMOTE_CATALOG_ALLOW_FILE_SOURCE).
daikoku.remoteCatalogJob.allowPreCommandfalseAllows pre_command on the file source (DAIKOKU_REMOTE_CATALOG_ALLOW_PRE_COMMAND).
daikoku.remoteCatalogJob.allowedHosts[]Hosts the http, github and gitlab sources may call. Empty: any. A list or a comma-separated environment variable.

Each key has an environment variable, e.g. DAIKOKU_REMOTE_CATALOG_JOB_ENABLED, DAIKOKU_REMOTE_CATALOG_ALLOWED_HOSTS. The job runs every enabled catalog whose scheduling is on.

A catalog using a disabled file source or pre_command is refused when saved (400). One saved before the instance disabled it fails each run, with the variable to set in the error.
